# D1 图片存储约定

用户已明确要求不使用R2。保留正式在线版目标，图片分片存D1；无需开通R2订阅。以下内容替代原设计中的图片桶约定。

## 接口

`image-storage.js` 导出 `D1ImageStorage` 和 `getImageStorage(env)`。工厂默认 `new D1ImageStorage(env.DB)`，测试可显式注入 `env.IMAGE_STORAGE`；生产无模拟开关。Queue通过此工厂写图；HTTP先检查作品归属，再通过私有SQLite DO调用此工厂逐片读取，避免公共HTTP请求承担大图解码。密码计算也由私有DO串行执行，不降低scrypt保护强度。DO不持久保存密码或图片。

`put/get/delete` 形状兼容既有内部图片桶接口。get返回size/httpMetadata/body，body为逐片查询、解码的ReadableStream；只返回completed对象。put收到Uint8Array和options.customMetadata.job_id/artwork_id，对应一个已经running的任务。对象key为Queue生成的artworks/用户ID/作品ID.扩展名。

## 数据表（Store代理维护schema）

- `image_objects(object_key TEXT PRIMARY KEY,job_id TEXT NOT NULL REFERENCES jobs(id),mime TEXT NOT NULL,byte_size INTEGER NOT NULL,encoded_size INTEGER NOT NULL,chunk_count INTEGER NOT NULL,metadata_json TEXT NOT NULL,sha256 TEXT NOT NULL,completed INTEGER NOT NULL DEFAULT 0 CHECK(completed IN(0,1)),created_at TEXT NOT NULL)`。
- `image_chunks(object_key TEXT NOT NULL REFERENCES image_objects(object_key) ON DELETE CASCADE,chunk_index INTEGER NOT NULL,body_base64 TEXT NOT NULL,PRIMARY KEY(object_key,chunk_index))`。
- jobs增加 `storage_reservation_bytes INTEGER NOT NULL DEFAULT 0`。

## 容量与状态

contracts已提供：MAX_IMAGE_BYTES=20MiB，IMAGE_CHUNK_BYTES=768KiB原始字节（每片base64最大1MiB，小于D1单行2MiB），IMAGE_STORAGE_BUDGET=320MiB，IMAGE_RESERVATION_BYTES=ceil(20MiB/3)*4。

预算使用 `SUM(image_objects.encoded_size)+SUM(jobs.storage_reservation_bytes)`。reserveGeneration在同一原子batch中预占算力和最坏图片大小；超预算时不创建job、不发送Queue、不调用收费模型，抛409 `storage_capacity`。成功、明确失败、人工结算释放storage_reservation_bytes；unknown保留尚未落图片的预留。

put创建pending元数据并把对应running job的storage_reservation_bytes置0，二者必须同一batch，避免已分配图片预算与预留双重计算。逐片单独编码/写入，避免整张大图的完整base64字符串、巨型batch和数字数组。最多20MiB图片27片，控制免费单次调用D1查询次数。全部写入后才标completed=1。

同key同摘要的完整对象可以复用，不覆盖不同内容。写入中断的残片不对用户显示，仍计算预算。Store明确失败或人工结算时，只清理该任务关联的completed=0残片；已完成对象与作品不自动删除。

当前仍保留所有成功作品，最近4张上限尚未启用。网页把storage_capacity视为明确未受理，不能进入“上次请求结果未知”的锁定状态。
